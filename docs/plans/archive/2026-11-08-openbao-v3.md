## Binding requirements and review focus

Already decided by the user-supplied handoff, as qualified by accepted D1 and D2:

- Managed OpenBao is the fresh-install default; Local is an explicit opt-out. Existing installations require an explicit migration, never an automatic provider switch.
- Persistent production-mode OpenBao; never dev mode or reinitialization of populated storage. Start with 512 MiB memory, a 0.5-vCPU soft budget, and 1–2 GiB anticipated data, measured rather than advertised as sufficient.
- Keep `https://vault.devkit.<configured-domain>/ui/` and use the existing Traefik. LAN and remote Tailscale need trusted HTTPS and native OpenBao authentication.
- Store Devkit system and integration secrets in OpenBao once ready; only protected authentication bootstrap material may remain outside. No root/unseal/recovery material in Devkit settings or agent output.
- Immutable project, branch and worktree IDs; worktree > linked branch > project precedence; explicit ownership and reveal; project-scoped API credentials cannot access system or other-project secrets. No claim of OS isolation from the unrestricted host user.
- Every UI action has a documented, scriptable CLI equivalent. CLI does not bypass backend authorization. Secret auditing uses a protected authenticated-actor audit stream; existing best-effort public history is insufficient and `DEVKIT_BY` is never an authority source.
- Confirmed branch/worktree secret-scope retirement retains secrets for 7 days; project retirement gives all recoverable descendants 30 days. Record observed external removal separately and start the deadline at confirmed retirement, not a guessed past deletion time. Restore before expiry, then destroy retained versions and metadata safely. No source/Git deletion by the secrets subsystem.
- Both Codex and Claude Code receive a canonical, versioned skill and preserved managed instruction blocks. Skills do not grant privileges.
- Preserve `devbox.json` and `DEVBOX_*` compatibility, existing previews/data, user edits, standard-library Go and committed `web/dist` assets.

Review focus, with owning tasks:

1. Scope confusion or credential propagation can expose system/other-project values through normal APIs: Tasks 1/7 must reject requests outside the supplied grant and avoid passing service credentials to child processes. Same-user shell/Docker bypass is explicitly outside D1, not a test failure to hide.
2. A cold, sealed vault must not require Cloudflare, Traefik TLS or the vault-backed web session key to recover: Tasks 2–4 cover this circular dependency.
3. Name/path reuse, detached or temporary review checkouts, missing mounts and external Git operations must not rebind old secrets: Tasks 5–6 cover ambiguity and reconciliation.
4. Failed dual writes, version limits and cleanup/restore races must not destroy recoverable data: Tasks 5, 7 and 10 cover journals, CAS and virtual time.
5. Plaintext must not enter Docker configuration, job streams, public inventories, KeepAlive state or agent transcripts except intentional reveal/consumer output: Tasks 3–4, 7–9 and 12 test these boundaries.

## Proposed component boundaries and contracts

### Trust, transport and bootstrap

- Add `devkit secrets serve` as a same-user service using the existing user-service conventions. Keep its configuration/state private from other users and outside project trees. No dedicated OS account, worker runtime, T3 launcher replacement or Docker privilege change is required by D1. Ordinary devkit commands still never invoke sudo.
- Use a private local Unix socket for CLI transport and the existing authenticated same-origin dashboard adapter. Socket permissions restrict other host users; peer UID identifies the host account, **not** whether a same-user process is human or agent. Never use `DEVKIT_BY`, cwd or a caller-supplied ID as authentication.
- The operator explicitly provisions/revokes project-bound grants through operator-authenticated commands/UI. A grant records actor label, project, allowed operations/resources, expiry and revocation generation. The CLI selects an already-issued grant from private user configuration for the verified project context; its requested IDs must be within that grant. A grant for A cannot become a B/system grant through flags, changed cwd or changed display identity. User-owned grant files can be read by another process of that user: this is the documented D1 limitation.
- Keep normal project secret commands on the project route; system integration/settings/maintenance commands use a separate explicit operator-authenticated route. Never automatically retry a denied project request with service/operator authority. Provide CLI grant list/create/revoke equivalents under `secrets access` and an operator access-management UI. Do not claim this stops an unrestricted same-user process from obtaining the operator's credentials.
- Separate broker/OpenBao roles for system integration access, per-project KV access, cleanup and operator maintenance. Project grants never yield service tokens or accept arbitrary OpenBao paths. Runtime credentials cannot initialize, unseal, manage arbitrary policies, restore snapshots or generate root access. Retire bootstrap root access after restricted roles and independent native-UI human login are tested.
- Keep T3, Codex, Claude, hooks, Git operations and Docker execution where they run today. Strip service/operator authentication from child environments and keep it out of project files, command arguments and logs. A socket or separate process alone is not an OS security boundary against that same user.
- Bootstrap and recovery use an explicit human ceremony independent of project grants and the vault-backed web-session secret. Recovery material goes directly to a controlling terminal or human-controlled encrypted ceremony, never ordinary stdout, JSON, jobs or model output. Remote first-run UI authenticates via an operator-issued one-use pairing credential after host bootstrap; the wizard hands recovery-material handling to that human channel. Same-user arbitrary-code attacks on the ceremony remain outside D1. All other wizard steps have CLI equivalents.
- Human native OpenBao login remains separate from the Devkit browser cookie. Native administrative changes may drift Devkit-managed paths: report and reconcile, never silently grant or delete because a raw path appeared.

### Durable registry and provider behavior

Proposed state paths under `stateDir()/secrets` (normally `~/.local/state/devkit/secrets`), following existing `DEVKIT_STATE_DIR`/XDG conventions. Directories are owner-only; tests use temporary roots. OpenBao storage remains outside disposable preview volumes:

```text
registry.json                 schema version + generation + resources + grants metadata
operations/                   durable non-secret migration/cleanup operation journals
backups/manifest.json          backup IDs/checksums/version/generation/destination metadata
openbao/data/                 persistent Raft storage, independent of previews
openbao/audit/                private audit sink with rotation
```

Runtime credential material belongs under a private memory-backed `$XDG_RUNTIME_DIR/devkit-secrets/`, with validated ownership/permissions and no persistent fallback. Service identity and operator/project grant files live under private `configDir()/secrets` using existing `DEVKIT_CONFIG_DIR` conventions; project grants never contain the service credential. These permissions protect against other users, not arbitrary same-user code. Backups never bundle recovery keys. No new `/var/lib` or privileged `/run` provisioning is required for agent isolation.

Registry schema v1 records random IDs from `crypto/rand`, kind, owner project ID, parent IDs, aliases, verified Git-common/admin-directory anchors, branch ref observations, checkout association, state, generation, timestamps, deadline and active references. Locators are evidence, never identity. Include an installation ID to detect copied/restored state. Keep preview IDs and the existing UI join keys separate.

Use an exclusive process lock, bounded reads, no-follow/pinned filesystem operations, generation checks and atomic write/fsync/rename for registry publication. No values in registry/journal; incomplete or incompatible state fails closed. Journals bridge registry/OpenBao changes, because a JSON file and a remote KV write cannot be atomic together. External Git state is observed and revalidated; the secrets subsystem does not journal or execute Git mutations. Record intent before an external mutation and resume by operation ID/CAS rather than repeating an acknowledged mutation.

Identity rules:

- Explicitly enroll verified main and linked checkouts; list all local branch refs, including branches with no worktree. Never enroll discovery candidates automatically.
- A confirmed registry rebind after an external rename/move preserves the immutable ID after preflight/revalidation. Devkit performs no Git rename/move. Recreated names get new IDs; clones and copied metadata are not automatically the same project.
- External branch rename/delete/recreate cannot always be distinguished by Git state or commit equality. Quarantine ambiguous associations and require operator reconciliation; do not infer inheritance from equal tips or names. A reused admin directory/path alone is insufficient.
- Detached HEAD inherits project only unless an explicit authorized association exists. Switching branches updates verified linkage while retaining worktree-owned secrets. Review scratch worktrees never acquire an automatic persistent scope or silently inherit the invoking branch's secrets.
- Missing directories, incomplete inventory or unavailable mounts do not prove deletion. Registry tombstones survive names being reused.

One key per KV entry, using the handoff's namespaces; encode validated key names and IDs, never accept caller-supplied mount/API paths. Use KV metadata for listing/history, CAS for changes, and separate explicit value reads. Source/owner/effective metadata is returned for every candidate, without plaintext. Pending-deletion ancestors deny descendant access; other-project IDs return an authorization failure without disclosing their metadata.

The Local provider uses the same authorization, registry, precedence, versions and cleanup contract with private local storage, clearly labeled **not encrypted at rest by OpenBao**. Do not invent custom cryptography. Selecting Local never exports vault values automatically. Missing legacy provider configuration retains existing behavior until an explicit migration; fresh setup records the default choice.

Migration stages: preview selected sources/consumers without values → checkpoint original non-secret schema and source ownership → read selected source privately → write target with CAS → compare readback in memory → test consumer → atomically switch reference → restart/reload relevant consumer → re-test → explicitly approve retirement of exact unchanged legacy sources. A source modified concurrently is retained and flagged. Never delete externally managed env/command secrets. Retain an encrypted rollback artifact until acceptance; no new plaintext backup of credentials. Scan known generated configs, Compose overrides and Docker configurations with sentinels, not users' entire home directory. Do not promise secure erasure from SSDs or old backups; recommend credential rotation where old plaintext copies existed.

For managed Cloudflare DNS, replace value environment variables with lego `_FILE` references to private tmpfs-backed files mounted read-only. Handle refresh and consumer reload explicitly; some consumers read credentials once. On reboot the runtime directory is empty and vault-required consumers wait for unseal. Never carry previous plaintext across a reboot as fallback. An already running consumer may retain a previously delivered value in memory; new broker fetches fail closed and status must distinguish this from a vault read succeeding. Validate each other DNS provider's file-input support rather than assuming all custom names support it. Unsupported safe delivery blocks managed setup for that provider and reports the exact limitation.

`secrets run` injects only selected authorized effective values into the child process, does not print them, strips broker/OpenBao/system authentication from the child environment and preserves exit status/signals. It cannot prevent the child from printing values. Compose integration uses reference-only saved configuration and runtime secret files; never resolve plaintext into `<common>/devkit/runs/*/compose.json`, build args or image layers. Rotation does not automatically rotate a remote database password: adapters must perform and report the remote change or label the operation as stored-value rotation.

Selecting a project/branch/worktree in the secrets UI or passing CLI selectors only changes the requested secret context. It never changes a Git branch, worktree, or shell directory. `secrets resources bind ID --to CANDIDATE_ID` previews association with a verified existing inventory candidate; confirmed apply changes registry metadata only. `resources retire` uses the same preview/confirmation/state machine as `cleanup schedule`; it is not a filesystem/Git delete command. ## Execution tasks and dependencies

## Migration and rollback checkpoints

| Checkpoint | Safe stop / rollback |
|---|---|
| Before service bootstrap | Existing host unchanged; provider migration is not selected automatically. Remove only newly created empty test/service artifacts after exact ownership checks. |
| Vault initialized, before credential cutover | Preserve data and initialization identity. Disable routing/service if needed without deleting its volume. Continue recovery with original ceremony; never “fix” by reinitializing. |
| References prepared, before activation | Legacy consumers still use original sources; discard only unactivated metadata under the migration ID. Do not leak a new plaintext config backup. |
| Cutover completed, source retirement pending | Roll back through explicit verified migration plan; no background fallback. Keep new vault values protected and do not replay already completed external writes. |
