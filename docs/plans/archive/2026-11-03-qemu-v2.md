## Behavior

Projects declare optional `vms` entries in devkit.json (or legacy devbox.json):
`{"project":"example","vms":[{"name":"example-worker"},{"uuid":"…"}]}`.
Each entry has exactly one exact name or valid UUID; no glob/prefix matching.
Names match case-sensitively; UUIDs match case-insensitively. UUID claims take
precedence over name claims. Duplicate live identifiers and competing project
slugs remain unassigned with a visible explanation. Repeated claims across
worktrees of the same project are not conflicts. Association is descriptive,
never an authorization boundary.

Discover recipes using existing Docker worktree labels and the configured harness
worktree glob, plus the current CLI directory and readable QEMU working directories
(walk to the nearest recipe). For VM-only/libvirt projects, host config `vm_projects`
explicitly lists project directories (absolute or ~/ paths). This is discovery of
recipes, not inferred ownership: VMs only match declared name/UUID selectors.
A VM-only recipe needs no Compose files or hooks. Read no raw process environments,
run no project hooks, and return no discovery/disk paths in VM API metadata.

Use bounded optional Docker probing and limit discovery to 128 unique recipes.
Provider failures/invalid recipes warn without hiding VM inventory. Project edits
are picked up on the next inventory refresh (existing five-second cache).

Add `project` and optional `project_note` fields to each VM. Group the dashboard
and CLI by the existing project slug, sorted by slug, with Other VMs last. Filters
include project names; counts reflect displayed members, connection disclosures
and all prior metadata remain available. JSON remains the flat inventory with
project metadata. UI never treats project names as unescaped HTML.
