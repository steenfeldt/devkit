**Trust model:** one trusted development-host user, not hostile tenants. One restricted OpenBao identity stays inside the backend and never reaches agent responses or child environments. **Scope boundaries:** manual unseal; no stored unseal/root key, auto-unseal, HA, new worker isolation, MCP, dynamic credentials, custom audit analytics or elaborate restore/upgrade UI. Show managed project-secret functions as unavailable when OpenBao is disabled. Existing installations migrate only through explicit verified import. ## Shared behavior and interfaces

- `vault_client.go` owns the bounded OpenBao HTTP/KV adapter; `secrets.go` owns scope resolution and operations. Expose only typed operations, never a raw OpenBao path/API proxy. CLI reaches the same backend through a private local Unix socket; authenticated web handlers call the same operation layer. Reuse the user-service lifecycle; no separately hardened execution environment.
- Registry records installation/project/branch/worktree IDs, verified Git anchors/linkage, owned key paths and cleanup state/deadlines. Use a lock, atomic replace and generation checks; a small durable operation record resumes interrupted vault/registry changes. Names/tips/path reuse never transfer secrets. Missing paths or incomplete inventory are not proof of deletion; exclude temporary review checkouts. Explicit rebind preserves identity after verified external moves/renames.
- KV paths follow the guide. Worktree > explicitly linked branch > project precedence; detached worktree inherits project only without a verified branch link. Lists/history contain metadata, ownership and effective source, never values. Updates use expected version/CAS; overriding an inherited value writes to the chosen child scope. Avoid automatic KV version eviction within promised recovery windows; configure a bounded retention policy and refuse unsafe writes before silently destroying recoverable versions.
- CLI: `vault status/setup/init/provision/unseal/ui/backup/health/update`; `secrets context/list/generate/set/get/update/rotate/delete/run/history/restore`; `secrets resources register/list/bind/reconcile/retire`; `secrets cleanup preview/status/restore/purge/config`; integration configure/status/reveal/rotate and Git binding; `agents skills install/status/repair`; `doctor --agents`. Each UI operation maps to one of these, with command help, metadata-only JSON, explicit selectors and sanitized errors. Values enter by protected prompt/stdin; reveal is explicit; generation never prints by default. `secrets run` injects only selected effective values and preserves child exit status/signals.
- Resource retirement changes secret metadata only, not Git/files. It previews exact owned keys and requires confirmation; active worktree links block branch retirement. Restore recovers secrets/registry and requires verified binding before normal context access; it does not recreate Git resources. Rotating a stored password does not change it in an application automatically; deleting a saved password does not revoke it remotely.
- **Cleanup settings:** host-level defaults are branch 7 days, worktree 7 days, project 30 days. Each retention accepts a positive duration or `never`; `automatic` can be disabled globally. Expose authenticated UI controls and `secrets cleanup config show/set` with `--branch-retention`, `--worktree-retention`, `--project-retention`, `--automatic on|off`. Validate bounds and show affected behavior before applying; no environment-only hidden setting.
- **No automatic cleanup:** do not automatically retire, soft-delete or purge secrets. Explicit retire/delete/restore and previewed, confirmed manual purge remain available. Confirmed retired secrets stay recoverable without automatic expiry destruction. `never` similarly prevents automatic expiry for the selected resource type. Do not delegate expiry to OpenBao TTLs that bypass these controls.
- **Deadlines:** normal retention starts at confirmed secret retirement, not an inferred Git deletion. Project retirement applies its selected retention to recoverable descendants and must not shorten a pre-existing longer/indefinite protection silently. Settings changes affect new retirements; retain existing deadlines as metadata while automation is off. Re-enabling automation requires an explicit preview/confirmation of any overdue batch before resuming its purge. No immediate hidden catch-up. Existing settings/deadlines survive restart and backup/restore. Backup retention is separate and may preserve deleted values.
